이 문서는 [영어판](../concepts.md)의 번역이며, 내용이 다르면 영어판이 우선한다. 번역 기준 버전: **0.3.0**.

# 개념과 한계

receipt는 명시적으로 요청한 전송 한 건에서 이 래퍼가 관측할 수 있었던 내용을 기록한다.
세션 소유권을 옮기거나 모델이 지시를 활용했다고 인증하지 않는다.
기록한 의도마다 무작위 시도 ID를 부여한다. 프로세스 시작에 실패해도 마찬가지다.
`--retry-of`는 지시 바이트가 같은 새 시도를 같은 엔진의 명시적 재시도 그룹에 연결한다.
엔진 간 재시도 그룹은 지원하지 않는다. 프로세스나 상태를 바꾸는 RPC를 자동으로 재시도하지 않는다.

## 독립된 사실

공통 사실 키는 같지만 제공하는 증거는 엔진마다 다르다.
전송하지 않았거나 프로세스 시작에 실패했다고 확인된 경우를 제외하면, 증거가 없는 사실은 `unknown`(알 수 없음)이다.

| 사실 | Codex | Claude headless |
|---|---|---|
| attempted | 데몬 turn/start 전송 경계에 도달했거나 프로세스가 시작됐을 가능성이 있음 | 프로세스가 시작됐을 가능성이 있음. 의도만 있으면 false |
| dispatched | 프로세스가 생성됐거나 데몬 turn/start를 보내기 직전임 | 프로세스 생성됨. 전송 전은 false, 프로세스 시작과 기록 사이의 공백은 unknown |
| process_started | 자식 프로세스 생성 관측. 데몬 모드는 unknown | 자식 프로세스 생성 관측 |
| process_exit_code | 래퍼가 자식 프로세스의 종료 상태를 회수했을 때 관측 | 동일. 릴레이 실행 파일을 썼다면 릴레이에 대한 관측 |
| target_input_confirmed | 식별된 턴에 보존된 사용자 메시지의 지시 바이트가 정확히 일치함. observed | 사전 점검 뒤 조건을 충족하는 유일한 user의 디코딩된 UTF-8이 지시와 정확히 일치함. observed |
| turn_started | 보존한 task_started에서 observed. 없으면 유일하게 연결된 exec 스트림의 시작 보고로 reported | 항상 unknown. 지원 프로필에 독립적인 작업 시작 이벤트가 없음 |
| turn_status | 정확한 원본 종료 기록 또는 정확한 ID의 데몬 상태에서 observed. 없으면 스트림 종료 보고로 reported | 세션에 연결된 스트림 result 하나로 reported. 원본 흔적만으로는 전체 턴 상태를 확정할 수 없음 |
| completed_at | 보존한 성공 종료 기록의 타임스탬프. observed | 항상 unknown. 원본 작업 완료 시각이 없음. assistant 시각이나 결과 수신 시각으로 대신하지 않음 |
| final_output_sha256 | 안전한 원본 최종 출력에서 observed. 없으면 완료된 스트림의 안전한 메시지로 reported | 선택한 상태가 completed일 때만 안전한 result.result로 reported. 원본 텍스트 해시는 보조 정보 |
| model_read_or_used | 항상 unknown | 항상 unknown |

저장된 의도만으로는 시도했다고 보지 않는다.
`attempted=true`(시도했을 가능성 있음)는 요청이 서버에 도달했을 수 있다는 뜻이다. 전달 확인을 뜻하지 않는다.
실제 전송에 앞서 내구성 있게 사전 기록을 남겨야 하므로 `dispatched=true`(전송 경계 기록됨)도 수신 증거가 아니다.
예전의 초기 `attempted` 이벤트는 의도로 해석한다. 이후 제어 기록으로 전송 여부를 판단한다.
거절한 실행에는 `rejection_reason`(거절 사유)이 들어간다. inspect/list에는 `not sent`(전송 안 됨)를 표시한다.
예전의 일반적인 오류는 사유를 알 수 없다는 메시지를 유지한다. 과거 원인을 새로 지어내지 않는다.

`task_complete`는 생명주기 이벤트다. 반드시 성공을 뜻하지는 않는다.
Codex 0.163.0은 실패에도 이 이벤트를 쓰며 `error`가 null이 아니다.
프로세스 종료 코드 0도 충분하지 않다.
프로세스가 끝나도 대상 관측은 unknown일 수 있다. 반대로 래퍼의 종료 관측이 유실되어도 원본 턴은 완료될 수 있다.

## 평가 수준

보존하는 원본 바이트는 지시, 선별한 원본 JSONL 줄 또는 Antigravity leaf wire 필드다.
해시, 원래 바이트 범위, 생략 정보는 포착 출처를 설명한다.
receipt와 조회 결과는 이 바이트와 명시적으로 기록한 제어 관측에서 결정적으로 도출한 해석이다.
래퍼의 의도와 프로세스 생성은 로컬 관측이다. 전달을 입증하지 않는다.
원본의 정확한 입력 확인은 더 강한 증거다. 그래도 모델 입력 노출이나 활용을 입증하지 않는다.
암호학적 원본 인증, UASS 적합성, 원본 엔진 전반의 호환성을 주장하지 않는다.

0.1.1부터 각 사실에는 `fact_levels`(평가 수준)의 `observed`(관측됨), `reported`(보고됨), `unknown` 값이 있다.
observed 프로세스 사실은 래퍼가 시작한 자식 프로세스를 다룬다.
observed 턴 사실은 원본 기록이나 기존의 정확한 ID에 대한 데몬 상태 관측을 다룬다.
exec JSON 스트림의 생명주기 주장은 reported다. 대상 입력 확인이 아니다.
요약은 observed 사실을 우선한다. 별도의 `reported`와 `observed_facts`(관측 사실) 보기도 유지한다.
사람이 읽는 출력에는 `completed (reported)`처럼 상태의 수준을 표시한다.
`identity_levels`(식별 정보의 평가 수준)는 요청한 ID, 스트림 보고, 원본 연결을 구분한다.
스트림에 턴 ID가 없으면 만들어 내지 않는다. 로컬 receipt 수신 시각을 원본 `completed_at`으로 쓰지도 않는다.

프로세스가 성공하고 완료가 reported이면 래퍼는 종료 코드 0을 반환한다.
원본 관측을 사용할 수 없으면 경고도 낸다.
Codex의 observed 실패·중단은 reported 완료보다 우선한다. Claude는 아래의 충돌 규칙을 쓴다.
두 출처 모두 완료 증거가 없으면 원본 종료 코드가 0이어도 2를 반환한다.
증거 부족을 재전송 사유로 취급하지 않기 위한 정책이다.
출력 사용 가능 여부는 별개다. 대상 확인에 실패해도 안전한 스트림 최종 메시지를 요청한 파일에 쓸 수 있다.
출처는 `reported`로 기록한다. 이 파일은 출력의 증거일 뿐이며, 원본 전달·완료 시각·의미상 활용은 별개의 사실로 남는다.

## 엔진 식별과 Claude 결과 해석

엔진은 모델 이름과 별개로 명시적으로 정한다. 기본값은 `codex`다.
새 Claude 세션 UUID는 프로세스 시작 전에 요청에 확정해 저장하고 `--session-id`로 전달한다.
명시적 resume은 지정한 UUID를 유지한다.
init/result의 식별 정보가 불일치하면 스트림 주장과 원본 기록 연결은 무효다.
확인된 원본 user UUID는 `turn_key={kind: user_message, value: UUID}`와 조회의 `turn_id`가 된다.
이것은 메시지 식별자다. 검증된 실행 턴 ID가 아니다.
엔진 구분자를 붙여 서로 다른 엔진의 같은 원본 ID가 충돌하지 않게 한다.
엔진 정보가 생략된 기존 번들은 Codex로 해석하며 원형을 유지한다.

Claude 완료에는 세션에 연결된 유효한 result가 정확히 하나 필요하다.
`is_error=false`이고 `terminal_reason=completed`여야 한다.
`is_error=true`이면 failed(실패)다. 중지·중단 사유라면 interrupted(중단)다.
`subtype`은 성공 여부를 결정하지 않는다. subtype이 success여도 API 오류를 보고할 수 있다.
result가 없거나 중복되거나 형식이 잘못됐거나 식별 정보가 충돌하면 상태는 unknown으로 남는다.

`native_traces`(원본 흔적)는 연결된 합성 오류 assistant, 중단 user, assistant end_turn 표식을 보조 observed 사실로 보존한다.
이들은 전체 턴의 종료 이벤트가 아니다.
reported 완료가 오류·중단 흔적과 충돌하면 상태와 최종 출력은 unknown이 된다.
`claude_status_conflict`도 기록한다. 원래 보고는 계속 조회할 수 있다.
이때 원본 종료 코드가 0이면 래퍼는 2를 반환한다. 0이 아닌 다른 원본 종료 코드는 유지한다.

안전한 완료 `result.result`만 Claude의 최종 출력 파일과 reported 해시의 근거가 된다.
조건을 충족하는 마지막 원본 assistant 텍스트의 해시, 종료 사유, 타임스탬프는 보조 정보다.
비교할 수 있으면 `matches_reported_output`(보고된 출력과의 일치 여부)을 포함한다.
뒤에 나온 assistant가 생략되면 앞선 원본 해시를 최종 해시로 다시 쓰지 않는다.
복구는 입력 확인이나 원본 흔적을 추가할 수 있다.
하지만 유실된 result를 재구성하거나 원본 end_turn을 전체 턴 완료로 격상할 수는 없다.

### 부모 연결 사슬과 파생 연결 정보

새 관측에서는 assistant나 중단 표식의 parentUuid(부모 UUID) 연결 사슬이 정확히 일치하는 입력 user에 도달해야 한다.
연결 사슬은 사전 점검 뒤 선택한 추가 기록 구간 안에 있어야 한다.
중단 표식이 아닌 다른 실제 입력 user, 끊긴 연결, 구간 밖 연결, 중복 UUID, 순환이 있으면 연결할 수 없다.
명시적 promptId 충돌도 연결을 차단한다. 연결에는 위 조건을 충족하는 부모 사슬이 필요하다.

연결 사슬이 생략된 행을 지나면 `connection_projections`(파생 연결 정보)에 그 행의 uuid/parentUuid 값과 원본 줄 범위·해시만 담는다.
파생 데이터임을 표시한다. 이 정보는 보존된 원본 행이 아니다.
inspect와 verify는 원본 기록을 열지 않는다. 보존한 바이트와 파생 정보로 연결을 다시 도출한다.
이 연결은 보조 해시·흔적만 뒷받침한다. 위의 result 규칙은 그대로 적용한다.
연결 방식 표식이 없는 기존 관측은 명시적 promptId 해석을 유지한다.
저장 형식과 무결성 한계는 [참조](reference.md#번들-버전-1--해석-버전-2)에 있다.

## 질문과 재시도 그룹

`inspect`는 시도 ID나 엔진 구분자가 붙은 턴·메시지 ID에 대해 R1에 답한다.
`dup`은 같은 엔진의 명시적 재시도 그룹 안에서 R2에 답한다.
Codex는 기존 규칙을 유지한다. 입력이 확인된 서로 다른 스레드·턴 쌍 두 개면 중복을 확정한다.
Claude는 확인된 서로 다른 세션·사용자 메시지 쌍에 대해 reported 종료 결과도 필요하다.
입력 기록 두 개만으로는 충분하지 않다.

그룹의 모든 시도가 전송하지 않았다고 확인됐거나 입력 확인과 종료가 모두 확정됐을 때만 유효 시도를 정할 수 있다.
유효 시도는 성공한 완료 중 유일하게 가장 이른 것이다.
시각 누락, 미해결 시도, 동률이 있으면 unknown이다. 모두 해결됐지만 성공이 없으면 null이다.
Claude의 성공한 그룹은 completed_at이 unknown으로 남으므로 이 순서를 확정할 수 없다.
어떤 업무 효과가 중요했는지를 식별하는 것은 아니다.
`which`는 지시 SHA-256이나 포착한 경로로 R3에 답한다.
확인된 대상 매핑을 반환하고 확인되지 않은 시도는 별도로 나열한다.
삭제한 시도를 포함해 보존된 관측 범위 밖에서는 unknown을 그대로 유지한다.

## 복구와 경계

변경 불가능한 의도 매니페스트와 첫 체크포인트는 숨김 `.pending-*` 디렉터리에서 완성한다.
fsync 뒤 최종 시도 ID로 원자적으로 이름을 바꾼다.
초기화 프로세스가 강제 종료되어도 반만 작성된 번들은 게시되지 않는다.
숨김 비정상 종료 잔여물은 조회에서 제외한다. 초기화 프로세스가 실행 중이 아닐 때 삭제할 수 있다.
조회는 게시된 손상 번들을 건너뛰고 stderr에 분류된 경고를 낸다.
verify/export는 무결성 실패를 계속 보고한다.
건너뛴 번들이 있으면 중복이 없다는 결론이나 유효 시도 결론은 unknown이 된다.
forget은 손상 번들도 읽어 들이지 않고 삭제한다. 다만 실행 중인 기록 프로세스가 있으면 거절한다.

관측 체크포인트는 해시로 주소를 정한 변경 불가능한 JSON이다. 앞선 체크포인트와 연결된다.
체크포인트가 디스크에 기록된 뒤 CURRENT를 원자적으로 바꾼다.
비정상 종료 뒤에는 이전의 완전한 체크포인트를 안전하게 읽을 수 있다.
완전하지만 연결 사슬에서 벗어난 체크포인트는 검사하되 해석하지 않는다. 미완성 임시 파일은 무시한다.
복구는 과거 체크포인트를 보존하고 새 관측을 추가한다.
해시는 로컬 무결성 기준값이지 서명이 아니다. 바이트와 모든 기준값을 함께 바꾸면 이 장치를 우회할 수 있다.

일반 조회와 검증은 저장된 번들만 사용한다.
명시적 `recover`는 원본 rollout(원본 기록 파일)을 읽어 유일하게 정확히 일치하는 입력을 복구할 수 있다.
전송하지 않았다고 확인된 의도는 복구 중에도 원본 턴에 연결하지 않는다.
재전송, 데몬 재연결, 프로세스 종료는 절대 하지 않는다.
래퍼가 강제 종료돼도 원본 자식 프로세스는 계속 실행 중일 수 있다.
복구는 부분적인 턴을 관측할 수 있다. 필요하면 턴이 끝난 뒤 다시 복구한다.
시도별 잠금은 살아 있는 래퍼와 복구가 동시에 실행되지 않게 한다.
SIGINT/SIGTERM은 시작한 원본 프로세스 그룹에만 전달한다. 래퍼는 SIGKILL을 처리할 수 없다.

rollout 탐색은 로컬 Codex의 `sessions/**/rollout-*.jsonl` 구조를 지원한다.
맥락 압축은 턴을 끝내지 않는다. `compacted` 기록이 있어도 정확한 시작·입력 연결은 다음 작업 시작이나 일치하는 종료까지 유지된다.
맥락 압축 본문은 여전히 생략한다.
포착과 복구는 일시적으로 없는 증거를 기본적으로 최대 2초 다시 읽는다. 재전송하지 않는다.
영구적 오류는 즉시 멈춘다. 구체적이고 안전한 진단과 재조회 이력이 빠진 증거를 설명한다.
나중 재조회에 실패해도 앞선 성공 관측은 번들에 남는다.
현재 진단은 나중 실패를 설명한다.
Codex exec resume은 사전 점검 경계를 알 수 있도록 전송 전에 rollout이 있어야 한다.
스트림 스레드 ID 없는 Codex 복구는 전송 전에 없던 경로만 후보로 삼는다.
작업 디렉터리와 정확한 입력이 일치해야 하며 후보가 하나여야 한다.
후보가 모호하면 unknown으로 남는다.
32 MiB 초과 파일, 잘못된 JSON, 익숙하지 않은 이벤트 형식, 사용할 수 없는 경로는 unknown 관측을 낳는다.
지시 파일은 1 MiB로 제한한다. 데몬 턴 목록 페이징은 지원하지 않는다.
새 idle(유휴) 데몬 스레드는 rollout 경로·파일이 없고 턴 목록이 비었거나 아직 생성되지 않았다면 0바이트 사전 점검을 사용한다.
첫 턴 뒤 경로를 갱신한다. 이전 턴이 있는 스레드의 rollout이 없으면 거절한다.
`notLoaded`(아직 로드되지 않음) 스레드는 앱에서 열거나 exec resume을 쓰라는 안내와 함께 거절한다.
이 CLI는 스레드를 로드하거나 소유권을 가져오지 않는다.

Claude는 기록한 cwd(작업 디렉터리)의 프로젝트 폴더에서 정확한 세션 파일만 읽는다.
관측된 경로 인코딩에 따라 슬래시를 하이픈으로 바꾼다.
resume은 사전 점검 때의 길이와 접두부 해시를 확인한다.
전송 전에 그 파일이 없으면 reported 실행은 성공할 수도 있다.
하지만 복구 뒤에도 원본 기록 연결은 unknown으로 남는다. 재구성할 안전한 원래 경계가 없기 때문이다.

구현·검증한 동작은 [검증 기록](validation.md)에 있다.
실제 위임은 목표 10건에 도달했다. 다만 중복 판단 두 번을 넘어선 유용성은 여전히 평가하지 않았다.
엔진·버전 전반의 지원, 엔진 간 재시도, Claude IDE/데스크톱 포착, Claude Agent 도구,
원본 자동 탐색 서비스, 서명, 그래프 저장소, UI, Hub 통합은 구현하지 않았다.

원본 환경 검증은 호스트 한 대의 표본이다. 이식성이나 의미상 활용을 보장하지 않는다.

## 0.3.0의 실험적 Antigravity

[Antigravity 해석](agy.md)은 stream-NDJSON exec/new/resume과 선별 SQLite protobuf 필드를 추가한다.
native 해석은 verified 1.5.9 범위이며 버전·해시 불일치는 경고와 native 사실의 unknown 강등으로 처리한다.
입력 확인에는 이 자식 stream의 유일한 user-input index도 필요하다. 전체 상태와 최종 출력은 단일 유효 result의
reported 사실이다. 시작·완료 시각·모델 활용은 unknown이다. native 취소 흔적은 completed 보고를 무효화할 수 있다.
운영자가 2026-11-15에 기록한 native 실측은 [검증 기록](validation.md)에 있다.
